# 구현 설명 (코드 읽는 순서와 README와 달라진 점)

평가 기준 "이해도"에 대비한 문서다. 각 파일 머리 주석에 입출력과 원리가 있고, 여기서는 전체 흐름과 이유만 적는다.

## 전체 흐름

```
MLX90393 ×4 ─I²C→ hdl/i2c_master.v, hdl/mlx_reader.v      프레임마다 12채널을 레지스터에 올린다 (CPU 없이 동작)
                          │ Avalon
                 nios/main.c 프레임 폴링, 기준값 차감
                 nios/position.c  장착 보정 → 세제곱근 압축 → 정수 MLP → (x,y,z,ux,uy)
                 nios/signature.c 펜 내림 판정, 서명 시작/끝, 128×8 int8 전처리
                 nios/dtw.c  또는  hdl/dtw_accel.v + dtw_array.v  (SW[5]로 전환)
                 nios/decide.c    문턱 판정 → LCD, LED, 7세그
                 nios/ui.c + hdl/vga_ui.v  모니터 화면: 문자 80×30칸, 서명 칸 비트맵(하드웨어 선 그리기), 펜 커서
PC: pc/train_mlp.py(가중치) pc/collect.py(수집) pc/gate1.py(오차) pc/evaluate.py(평가)
```

읽는 순서 추천: `hw/dtw_ref.py` → `hdl/dtw_array.v` → `nios/signature.c` → `hdl/mlx_reader.v`.

## 핵심 원리 네 가지

**1. 왜 PE 배열로 DTW를 병렬화할 수 있나.** 칸 (i,j)는 (i-1,j), (i,j-1), (i-1,j-1)만 쓴다. 이들은 모두 i+j가 1 또는 2 작다. 그러니 i+j가 같은 칸(안티대각선)끼리는 서로 의존하지 않아 동시에 계산할 수 있다. `hw/dtw_ref.py`가 순서를 바꿔도 값이 같음을 보인다. 대역 ±16 안에서 안티대각선 하나의 칸은 최대 17개다.

**2. 왜 PE 33개인데 절반씩만 일하나.** PE 하나가 오프셋 d = i−j 하나를 맡는다(−16~+16). x는 위에서 아래로, y는 아래에서 위로 한 PE씩 이동한다. 샘플이 두 클럭마다 들어가므로 x[i]와 y[j]는 d = i−j인 PE에서 시각 i+j에 정확히 만난다. PE는 두 클럭에 한 번 일한다. 남는 클럭을 파이프라인으로 써서 첫 클럭에 L1 거리, 다음 클럭에 min+덧셈을 한다. 그래서 곱셈기가 없고 50 MHz를 넘긴다. 공유로 17개까지 줄일 수 있으나 설명이 어려워져 쓰지 않았다. 자원이 모자라면 그때 바꾼다.

**3. 왜 자기장에 세제곱근을 취하나.** 쌍극자 자기장은 거리의 세제곱에 반비례한다. 펜이 가까우면 수 mT, 멀면 수 µT로 범위가 천 배가 넘는다. 그대로 넣으면 MLP가 큰 값에만 반응한다. 세제곱근은 r⁻³을 r⁻¹로 만들어 범위를 약 10배로 줄인다.

**4. 왜 φ 대신 ux, uy인가.** 아래 "달라진 점" 2번.

## 모니터 화면 (2026-11-11 추가)

화면 구성과 이유는 `docs/vga-ui-mockup.html`(브라우저로 연다)에 있다. 구현은 세 층이다.

| 층 | 내용 | 메모리 |
|---|---|---|
| 문자 | 80×30칸, 칸마다 글자 7비트 + 글자색 4비트 + 배경색 4비트(16색 팔레트) | M4K 10개 |
| 비트맵 | 서명 칸 192×192픽셀 1비트, 화면에서 2배. 1픽셀 = 0.5 mm | M4K 9개 |
| 커서 | 좌표 레지스터와 비교기 | 없음 |

- **왜 문자 층인가:** 640×480 전체를 픽셀로 저장하면 1비트만 해도 307 kbit로, 남은 메모리(약 125 kbit)에 들어가지 않는다. 문자로 나누면 화면 전체가 2,400칸 × 16비트 = 38 kbit다.
- **막대를 어떻게 그리나:** 왼쪽부터 1/8~8/8칸을 채운 글자 8개가 폰트에 있다. 꽉 찬 칸 여러 개 + 마지막 한 칸으로 1픽셀 단위 막대가 된다.
- **폰트:** DejaVu Sans Mono(자유 라이선스)를 `pc/gen_font.py`가 8×16 1비트로 바꿔 `hdl/font8x16.v`를 만든다. Quartus는 이 표를 메모리 블록이 아닌 로직(약 820 LE)으로 만들었다. 메모리 블록이 부족하고 LE는 여유가 있어 그대로 둔다.
- **메모리 블록 정리:** DTW 템플릿 RAM `t_lo`가 4096×1 블록 32개로 만들어져 7개를 낭비하고 있었다. `max_depth = 512` 속성으로 25개가 되었다(대신 출력 선택 로직 약 170 LE). 전체는 100 → 98개다.
- **펜 있음 판정:** 센서 값이 기준에서 `PEN_PRESENT_LSB`(40 LSB, 추정) 이상 벗어나야 커서와 좌표를 보여 준다. 펜이 없을 때 MLP 출력(잡음)이 화면에서 돌아다니지 않게 하기 위해서다. 실측으로 조정한다.
- **숫자 갱신 주기:** 획과 커서는 매 프레임(50 Hz), 숫자와 막대는 5프레임마다(10 Hz). 50 Hz로 바뀌는 숫자는 읽을 수 없다.
- 화면 글자는 영문만 쓴다. 결과 문구는 `PERSON n` / `NOT ENROLLED`다.

**확인 못 한 것:** 실제 모니터에서의 표시(동기 신호 호환, 색, 글자 가독성), 화면 갱신이 50 Hz 루프에 주는 실제 부담.

## 노트북 화면 중계 (2026-11-16 추가)

모니터 없이 노트북에서 화면을 보려고 만들었다.

```
nios/ui.c → ui_cell() ─┬→ VGA 회로의 문자 RAM (모니터)
                       └→ nios/relay.c → JTAG UART → pc/screen.py → 노트북 창
```

- 화면 내용은 보드가 정한다. 노트북은 받은 대로 그리기만 한다. 그래서 "DE2가 표시까지 한다"는 구조가 유지된다.
- 보내는 형식은 `@`로 시작하는 글자 줄이다. 바뀐 칸만 줄 단위로 보내고(`@T`), 서명 칸의 선(`@L`), 지우기(`@K`), 커서(`@P`)를 보낸다. 로그 도구는 `@` 줄을 무시한다.
- 10프레임마다 한 줄을 통째로 다시 보내서, 노트북을 늦게 연결해도 6초 안에 글자가 다 찬다. 서명 칸의 획은 다음 서명부터 보인다.
- 노트북은 보드와 같은 폰트 ROM과 팔레트, 같은 Bresenham 순서, 같은 커서 모양으로 그린다(`pc/screen.py`의 `Screen`).
- 검증: PC에서 펌웨어를 돌려 만든 중계 줄을 노트북 프로그램이 받아, 펌웨어가 만든 화면과 2,400칸이 모두 같은지 비교한다(`run_checks.sh`).

**확인 못 한 것:** JTAG UART의 실제 전송 속도. 수집 모드에서는 로그(약 5 KB/s)와 화면(대략 1~6 KB/s, 추정)이 같은 통로를 쓴다. 느리면 보드의 메인 루프가 출력에서 기다리게 되고, 로그의 프레임 번호가 건너뛴다(`evaluate.py`가 빠진 프레임 수를 알려 준다).
